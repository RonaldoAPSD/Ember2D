ember2d: Full Scripting API Expansion + Sprite Mode Architecture Audit
========================================================================

CONTEXT

The goal is to give script authors maximum power to make any game genre — top-down
shooter, turn-based RPG, roguelike — using only .rhai scripts, without touching Rust.
A secondary goal is to ensure the engine architecture doesn't paint itself into a corner
when 2D sprite mode is added later.

This plan covers:
  1. The full scripting API expansion (all additions in one pass)
  2. An architecture audit documenting what would need to change for sprite mode

========================================================================
PART 1: FULL SCRIPTING API EXPANSION
========================================================================

All changes are additions to ScriptCtx in src/scripting.rs, with backing storage in
PlayState (src/play.rs) and AppState (src/app.rs).

------------------------------------------------------------------------
1. SHARED GLOBAL STATE
------------------------------------------------------------------------
Needed for: turn counters, player stats readable by enemy scripts, game flags,
            inventory counts.

  ctx.set_global("player_hp", 10);
  ctx.get_global("player_hp")       // returns Dynamic (int, float, bool, string)
  ctx.has_global("player_hp")       // returns bool
  ctx.remove_global("player_hp")

Implementation: Add globals: HashMap<String, rhai::Dynamic> to PlayState.
Expose read/write via ScriptCtx. Cleared on level load (use persistent store
for cross-level).

------------------------------------------------------------------------
2. RANDOMNESS
------------------------------------------------------------------------
Needed for: combat dice rolls, loot drops, procedural room layouts, enemy
            behavior variance.

  ctx.random_int(1, 20)        // inclusive range, returns i64
  ctx.random_float()           // 0.0..1.0
  ctx.random_bool(0.25)        // true 25% of the time
  ctx.random_choice(my_array)  // returns random element from an array

Implementation: Add rng: SmallRng to ScriptCtx (seeded from system entropy at
level start). Expose four functions.

------------------------------------------------------------------------
3. SPATIAL QUERIES
------------------------------------------------------------------------
Needed for: pathfinding, FOV raycasting, collision-aware AI movement,
            range checks.

  ctx.get_entity_at(x, y)              // first entity whose collider covers (x,y) — id or -1
  ctx.is_solid_at(x, y)                // bool — any solid collider at position
  ctx.find_entities_in_rect(x,y,w,h)   // array of ids with colliders overlapping rect
  ctx.get_distance(id_a, id_b)         // euclidean distance between two entities
  ctx.get_angle_to(from_id, to_id)     // radians — useful for aiming/shooting

Implementation: Iterate world.transforms + world.colliders at query time.
No spatial index needed for typical entity counts (<500). Add to ScriptCtx
with a read-only borrow of the world.

------------------------------------------------------------------------
4. ENTITY UTILITY QUERIES
------------------------------------------------------------------------
Needed for: safely checking if a target still exists before acting on its id,
            counting enemies remaining.

  ctx.entity_exists(id)          // bool — false if despawned
  ctx.count_by_tag("enemy")      // int — live entity count with tag
  ctx.get_collider_w(id)         // float — collider width
  ctx.get_collider_h(id)         // float — collider height
  ctx.is_visible(id)             // bool
  ctx.set_visible(id, false)     // hide/show without despawning
  ctx.get_z_order(id)            // int
  ctx.set_z_order(id, 5)         // change draw layer

Implementation: Direct lookups into world component maps. set_visible and
set_z_order go through the existing deferred mutation queue.

------------------------------------------------------------------------
5. MOUSE INPUT
------------------------------------------------------------------------
Needed for: point-and-click targeting, aiming in top-down shooters,
            editor-style games.

  ctx.get_mouse_x()             // cell-space x (same coordinate system as entities)
  ctx.get_mouse_y()             // cell-space y
  ctx.mouse_left_pressed()      // bool — frame of click
  ctx.mouse_right_pressed()     // bool
  ctx.mouse_left_held()         // bool — held down
  ctx.mouse_right_held()        // bool

Implementation: Pass MouseState into ScriptCtx alongside the existing
InputManager. Mouse position is already in cell coords in src/mouse.rs.

------------------------------------------------------------------------
6. CAMERA CONTROL
------------------------------------------------------------------------
Needed for: scripted cutscenes, multi-room scrolling levels, zoomed-out
            minimaps.

  ctx.get_camera_x()                          // float
  ctx.get_camera_y()                          // float
  ctx.set_camera(x, y)                        // override camera position this frame
  ctx.shake_camera(intensity, duration_secs)  // screen shake effect

Implementation: Add camera_override: Option<Vec2> and shake_state: Option<ShakeState>
to PlayState. Scripts write to it each frame via deferred mutation. Renderer reads
it during draw. Camera shake offsets the render origin by a decaying random value.

------------------------------------------------------------------------
7. CROSS-LEVEL PERSISTENCE
------------------------------------------------------------------------
Needed for: player HP/inventory surviving level transitions, run-wide score,
            unlocks.

  ctx.set_persistent("player_hp", 10)
  ctx.get_persistent("player_hp")      // survives load_level
  ctx.has_persistent("player_hp")
  ctx.clear_persistent("player_hp")
  ctx.clear_all_persistent()           // call on game-over/new game

Implementation: Add persistent: HashMap<String, rhai::Dynamic> to AppState
(lives outside PlayState, survives transitions). Expose via ScriptCtx.
clear_all_persistent() resets for new game.

------------------------------------------------------------------------
8. HUD / DRAW UTILITIES
------------------------------------------------------------------------
Needed for: inventory screens, dialog boxes, status bars, bordered menus.

  ctx.draw_box(x, y, w, h, fg, bg)          // border-only box using box-drawing chars
  ctx.fill_rect(x, y, w, h, ch, fg, bg)     // fill area with a character
  ctx.clear_hud()                            // remove all pending HUD draws this frame

Implementation: Add HudBox and HudFill variants to the existing HudDraw enum
in scripting.rs. Renderer handles them in the same HUD pass as draw_hud.
clear_hud() drains the pending draw queue.

------------------------------------------------------------------------
9. TIMERS
------------------------------------------------------------------------
Needed for: cooldowns (gun fire rate, ability recharge), delayed effects,
            scripted sequences.

  ctx.start_timer("shoot_cd", 0.5)     // countdown timer, keyed by name
  ctx.timer_done("shoot_cd")           // true when elapsed; auto-removes
  ctx.cancel_timer("shoot_cd")

Implementation: Store timers in the entity's rhai::Scope as __timer_<name>: f32.
Decremented by delta each frame before scripts run. timer_done returns true and
removes the key. Benefits from existing scope persistence; no separate data
structure needed; timer names don't collide between entities.

------------------------------------------------------------------------
10. COLLISION LAYERS / FINE-GRAINED FILTERING
------------------------------------------------------------------------
Needed for: bullets that only hit enemies, items only pickable by player,
            layered collision.

  ctx.get_collider_layer(id)           // string — e.g., "bullet", "enemy", "player"
  ctx.set_collider_layer(id, "enemy")

Implementation: Add layer: String to Collider component. on_collide callbacks
receive both entity ids — scripts check layers to decide whether to respond.

========================================================================
PART 2: SPRITE MODE ARCHITECTURE AUDIT
========================================================================

This is an audit only — no implementation. Documents what to avoid breaking
and what to change when sprite mode is added.

------------------------------------------------------------------------
RENDERER  (src/renderer/mod.rs)
------------------------------------------------------------------------
Current:
  Pixel buffer (minifb) drawn cell-by-cell using font8x8 glyphs.
  Cell size is 8x16 px.

Compatible:
  minifb writes directly to a Vec<u32> pixel buffer. Blitting a PNG's pixels
  into that buffer requires no new windowing code — just image loading.

What changes:
  The render loop that calls draw_char per entity would need a branch: if the
  entity has a SpriteSheet component, blit pixels instead of drawing a glyph.
  The cell grid and ASCII path remain intact.

Risk:
  The fixed 8x16 cell grid means "1 unit = 1 cell = 8x16 px". Sprites would
  need to align to this grid OR require a separate pixel-space coordinate mode.

Recommendation:
  Add an optional pixel_scale: f32 per entity to allow sub-cell or multi-cell
  sprite sizes without changing the coordinate system.

------------------------------------------------------------------------
ECS COMPONENTS  (src/components/)
------------------------------------------------------------------------
Current:
  Sprite holds glyph: char + colors.
  Transform uses Vec2 (f32) — works in either coordinate system.

What changes:
  Add a new SpriteSheet component:
    texture_path: String
    frame_w: u32
    frame_h: u32
    current_frame: u32

  Leave Sprite (ASCII) untouched. Renderer checks: if entity has SpriteSheet,
  use it; else fall back to Sprite. Allows mixed ASCII + sprite entities in
  the same level.

------------------------------------------------------------------------
LEVEL FORMAT  (src/level.rs)
------------------------------------------------------------------------
Current:
  TileRecord has glyph, fg, bg. No image field.

Compatible:
  RON is schema-flexible with Option<> fields. No breaking change to existing
  .level files.

What changes:
  Add to TileRecord:
    texture: Option<String>
    frame: Option<u32>

------------------------------------------------------------------------
SCRIPTING API  (src/scripting.rs)
------------------------------------------------------------------------
What to add when sprite mode lands:

  ctx.set_texture(id, "assets/hero.png")
  ctx.set_frame(id, 3)
  ctx.set_pixel_scale(id, 2.0)   // 2x size sprite

These are additive — current glyph/color API stays valid for ASCII entities.

------------------------------------------------------------------------
WHAT DOES NOT NEED TO CHANGE
------------------------------------------------------------------------
  - Input system     — key and mouse APIs are resolution-independent
  - Audio system     — no coupling to rendering
  - Collision system — AABB already uses f32, works in either coord space
  - Scripting engine — Rhai is completely renderer-agnostic
  - Entity/tag system — unchanged

------------------------------------------------------------------------
VERDICT
------------------------------------------------------------------------
The architecture is compatible with sprite mode as designed. No foundational
refactors are needed. Two things to avoid when implementing Part 1:

  1. Don't hardcode cell-unit assumptions into new spatial query math —
     use the existing CELL_W/CELL_H constants when converting, not magic numbers.

  2. Don't store pixel coordinates in Transform — keep world coordinates in
     cell units; let the renderer apply the pixel scale.

VERIFICATION
========================================================================

After implementation, write a single test script (demo/scripts/api_test.rhai)
that exercises every new function and confirm output via ctx.log. Then build the
demo dungeon into a turn-based roguelike using only the new API — if enemy AI,
combat, inventory, and HUD all work via scripting with no Rust changes, the
expansion is complete.
